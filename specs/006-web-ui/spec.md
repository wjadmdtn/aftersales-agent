# Feature Specification: 客服前端（用户端 + 人工工作台）

**Feature Branch**: `006-web-ui`

**Created**: 2026-11-10

**Status**: Approved — 负责人 2026-11-10 确认，可进入实现

**Input**: 订单详情页 + 用户对话页 + 人工工作台，流式对话、快捷转人工、状态可视化

## 背景与目标

后端已经有完整的 Agent 能力（意图识别、工具编排、转人工、政策问答），但**没有界面**。

这个 feature 做三个页面：

| 页面 | 使用者 | 作用 |
|---|---|---|
| **订单详情页** | 客户 | 展示当前订单，底部「联系客服」入口 |
| **用户对话页** | 客户 | 与 AI 对话，可随时转人工 |
| **人工工作台** | 客服人员 | 看排队、接会话、读上下文包、回复用户 |

**入口设计**：真实客服产品里，用户是在订单页点客服进来的，订单上下文由入口带入，而不是让用户背订单号。所以本 feature 的对话页**必须支持从订单页带着订单进入**：订单页底部客服图标 → 携带该订单 ID 打开对话 → 此后该会话的所有提问默认针对这笔订单。

订单详情页的订单数据来自后端已有的 `GET /orders/{order_id}`，不写死——页面显示的状态必须与 AI 查到的同一份数据一致，否则会出现「页面显示已支付、AI 说已退款」的矛盾。

**核心价值不是"好看的界面"，而是让系统可被观察**：评审者打开两个页面就能看到 AI 介入、转人工、人工接管全过程。

## 演示路径（验收基准）

一条路径必须完整走通，这是本 feature 的成功标准：

```
⓪ 打开「订单 ORD1002」详情页 → 看到订单号、状态（已支付）、金额 259.90、收货地址
① 点底部「联系客服」→ 打开对话页，顶部显示「正在咨询：ORD1002」；用户说「我要退款」
② AI 回复「即将为订单 ORD1002 提交退款 259.90 元，确认吗？」
③ 用户说「确认」→ AI 执行 → 「已为您提交退款」
④ 用户说「我要投诉」→ AI 回复「已为您优先接入人工客服」
⑤ 人工工作台侧边栏出现新会话，标红「高风险」
⑥ 人工点开 → 看到摘要、已尝试动作、优先级依据
⑦ 人工点「接入」→ 用户在对话页看到「人工客服已接入」状态
⑧ 人工发消息 → 用户端收到
⑨ 人工点「结束会话」→ 双方状态变「已解决」
```

**全程不能刷新页面，状态实时同步。**

## User Scenarios & Testing

### User Story 1 - 用户对话与流式回复 (Priority: P1)

用户在对话页发消息，AI 逐字输出回复。

**Why this priority**: 对话是基础，没有它其他功能无从谈起。

**Independent Test**: 发送「我要退款」（会话已绑定 ORD1002），回复以流式方式逐段出现。不直接用「我的订单到哪了」——本地 stub 需先登记该句，否则会走澄清。

**Acceptance Scenarios**:

1. **Given** 用户在对话页，**When** 输入消息并发送，**Then** 消息立即上屏，AI 回复逐字出现
2. **Given** AI 正在输出，**When** 用户想停止，**Then** 可以中断（非强制能力，不计入 Success Criteria）
3. **Given** 网络中断，**When** 回复到一半，**Then** 已输出的内容保留，显示可重试提示
4. **Given** AI 回复失败（降级），**When** 返回，**Then** 显示统一话术，提供转人工按钮

---

### User Story 2 - 状态可视化 (Priority: P1)

用户随时能看清当前由谁在服务。共四类状态（AI 接手中 / 排队等待 / 人工接手中 / 已解决），`handoff_requested` 并入「AI 接手中」不单列（见 FR-004）。

**Why this priority**: 转人工后如果用户不知道状态，会重复提问或误以为没人管。

**Independent Test**: 从 AI 接管 → 排队 → 人工接管 → 已解决，四类状态每个在界面上可辨识。

**Acceptance Scenarios**:

1. **Given** AI 正在服务，**When** 查看，**Then** 显示「AI 助手」标识
2. **Given** 用户已触发转人工，**When** 查看，**Then** 显示「正在接入人工客服」并禁用输入框
3. **Given** 人工已接入，**When** 查看，**Then** 显示「人工客服 小王 正在为您服务」
4. **Given** 会话已解决，**When** 查看，**Then** 显示「会话已结束」，输入框禁用

---

### User Story 3 - 快捷转人工 (Priority: P1)

对话内一键转人工，不用打字。

**Why this priority**: 用户着急时打字很烦。而且「转人工」三个字容易被误识别为其他意图。

**Independent Test**: 点击转人工按钮，直接进入排队，不经过意图识别。

**Acceptance Scenarios**:

1. **Given** 用户在对话页，**When** 点击「转人工」，**Then** 立即进入排队，显示排队状态
2. **Given** 已转人工，**When** 再次点击，**Then** 按钮禁用，不重复入队
3. **Given** 排队中，**When** 用户发消息，**Then** 提示「正在为您接入，请稍候」

---

### User Story 4 - 人工工作台：队列与接入 (Priority: P1)

客服看到排队列表，按优先级排序，点击接入。

**Why this priority**: 没有这个，转人工就是断头路。

**Independent Test**: 多个会话排队，高优先级排前面；接入后从队列消失。

**Acceptance Scenarios**:

1. **Given** 有会话排队，**When** 打开工作台，**Then** 侧边栏显示队列，高风险标红
2. **Given** 队列有多条，**When** 查看，**Then** 按优先级排序，同级按时间
3. **Given** 人工点击某会话，**When** 接入，**Then** 该会话移出队列，进入「我的会话」
4. **Given** 人工接入多个会话，**When** 切换，**Then** 可正常切换，各自独立

---

### User Story 5 - 上下文包展示 (Priority: P1)

人工接入前能看到 AI 做了什么，不用从头翻聊天记录。

**Why this priority**: 这是转人工体验的分水岭。做得差等于从头再来一遍。

**Independent Test**: 打开任意排队会话，能看到摘要、已尝试动作、优先级依据。

**Acceptance Scenarios**:

1. **Given** 会话在队列中，**When** 点击查看，**Then** 显示摘要（≤120 字）
2. **Given** 会话调过工具，**When** 查看，**Then** 显示「已查过：订单、物流」
3. **Given** 优先级为高，**When** 查看，**Then** 显示判定依据（如「风险触发：命中投诉词」）
4. **Given** 触发类型是风险，**When** 查看，**Then** 不显示 AI 建议（风险场景不应由 AI 出方案）

---

### User Story 6 - 人工回复与结束 (Priority: P2)

人工在工作台发消息，用户端实时收到；结束后双方状态同步。

**Independent Test**: 人工发消息，用户端看到；人工结束，用户端显示「已结束」。

**Acceptance Scenarios**:

1. **Given** 人工已接入，**When** 发送消息，**Then** 用户端实时收到
2. **Given** 人工已接入，**When** 用户发消息，**Then** 人工端收到，**AI 不出现在中间**
3. **Given** 人工点击「结束会话」，**When** 确认，**Then** 双方状态变「已解决」

---

### Edge Cases

- 两个人工作台同时接入同一会话
- 排队会话在用户端被刷新
- 人工发送消息时用户已断开（消息落库，用户重连后按 `seq` 补齐）
- 网络抖动导致的重复消息
- 人工端点未带 `agent_id` 握手（返回 4401）
- 高并发下队列排序错乱

**本 feature 不分页**：演示规模下会话列表与队列均为全量返回（上限 200 条），不实现分页。

## Requirements

### Functional Requirements

**用户对话页**

- **FR-001**: 发送消息后立即上屏，不等待服务端响应
- **FR-002**: AI 回复必须以流式方式逐字呈现
- **FR-003**: 流式输出中断时保留已输出内容，提供重试
- **FR-004**: 必须显示当前服务方（AI / 排队中 / 人工 / 已结束）。机器状态 `handoff_requested` 在同一请求内即迁移为 `queued`，界面上不可观测，合并到「AI 接手中」展示，不单列
- **FR-005**: 转人工必须支持一键操作，不经过意图识别
- **FR-006**: 转人工后输入框状态必须与服务状态一致（排队中禁用）
- **FR-007**: 会话 ID 必须在刷新后保持（不丢上下文）

**人工工作台**

- **FR-008**: 侧边栏必须显示队列，含会话摘要与优先级
- **FR-009**: 高风险会话必须视觉上突出（颜色区分）
- **FR-010**: 队列必须按优先级排序，同级按进入时间
- **FR-011**: 必须展示 Context Pack：摘要、已尝试动作、优先级依据、触发类型
- **FR-012**: 风险触发时不得展示 AI 建议
- **FR-013**: 人工可接入、拒绝、结束会话
- **FR-014**: 人工可同时持有多个会话并切换
- **FR-015**: 同一会话同时只能被一个客服接入

**实时性**

- **FR-016**: 用户端与人工端的状态变更必须实时同步
- **FR-017**: 消息传递延迟必须可感知地低（不轮询）
- **FR-018**: 断线后必须自动重连并补齐状态

**工程约束**

- **FR-019**: 所有数据必须来自真实后端接口与 WebSocket 消息，不得伪造状态
- **FR-020**: 不得为前端单独开后门接口
- **FR-021**: 前端构建必须通过类型检查与构建，构建失败不得合并（仓库不设 CI，由人工在合并前执行校验）
- **FR-022**: 后端不依赖前端构建即可启动与测试

**支撑能力（会话查询面）**

- **FR-029**: 用户端刷新后必须能从服务端恢复会话状态与历史消息（服务 FR-007、FR-018）
- **FR-030**: 人工端必须能查询自己已接入的会话列表（服务 FR-014、US4-4）
- **FR-031**: 后端必须以生产配置独立装配 Agent、转人工协调器与会话存储，无前端构建、无测试夹具时 `/agent/chat` 与 `/handoff/queue` 均可正常响应（服务 FR-019、FR-022）
- **FR-032**: 同一会话被两名客服同时接入时，必须只有一人成功，另一人收到明确失败提示（服务 FR-015）
- **FR-033**: 订单详情页必须展示订单号、状态、金额、收货地址、下单时间，数据来自后端 `GET /orders/{order_id}`，不得前端写死
- **FR-034**: 订单详情页底部必须提供客服入口；点击后打开对话页，并将会话绑定到该订单，此后用户无需再说订单号
- **FR-035**: 会话绑定的订单号必须随会话持久化，刷新或重连后仍然生效（服务 FR-007）
- **FR-036**: 对话页必须显示当前绑定的订单，允许用户切换到其他订单（沿用现有「消息中出现订单号即切换」的能力）；切换后以最新绑定为准，刷新后恢复最新绑定

### Key Entities

- **会话**：会话 ID、用户 ID、订单号、状态、当前服务方
- **消息**：发送方（用户 / AI / 人工）、内容、时间、是否流式
- **队列项**：会话 ID、优先级、摘要、触发类型、进入时间
- **上下文包**：摘要、已尝试动作、优先级依据、AI 建议

## Success Criteria

### Measurable Outcomes

- **SC-001**: 演示路径 10 步（第⓪步订单页入口 + ①~⑨ 九个交互步）全部可走通，中途无需刷新
- **SC-002**: 流式回复首字延迟 < 2s
- **SC-003**: 状态变更在两端同步延迟 < 1s
- **SC-004**: 人工端展示的 Context Pack 字段完整率 100%
- **SC-005**: 页面在 1280×720 与 1920×1080 下均可正常使用
- **SC-006**: 前端构建成功，无 TypeScript 错误

## Assumptions

- 不做用户登录，会话用 localStorage 的 sessionId 标识
- 人工工作台不做账号体系，固定演示账号
- 不做移动端适配（1280 起）
- 实时通信用 WebSocket，两端共用一套

## 范围外

- 用户注册登录
- 商品浏览、下单支付
- 客服排班、绩效统计
- 多租户
- 国际化

## 已确认决策

| # | 问题 | 结论 |
|---|---|---|
| 1 | 实时通信 | **WebSocket，两端共用一套** |
| 2 | UI 库 | Element Plus |
| 3 | 页面范围 | 订单详情页 + 用户对话页 + 人工工作台 |

**为什么不用 SSE**：SSE 是单向的（服务端→浏览器）。用户端不只是收 AI 回复，
还要收**人工客服发的消息**——那条消息由服务端主动推给用户，
SSE 做不到，除非为每个用户再维护一条推送通道。

WebSocket 双向，收发同一条连接，两端共用一套实现。

## 实时通信要求

- **FR-023**: 用户端与人工端共用同一套 WebSocket 协议
- **FR-024**: 连接断开必须自动重连，采用指数退避
- **FR-025**: 重连后必须补齐断线期间的消息与状态（按 `seq` 增量补齐；本 feature 不实现"未读"标记）
- **FR-026**: 必须有心跳机制，避免中间设备断开空闲连接
- **FR-027**: 消息必须携带序号或 ID，前端据此去重
- **FR-028**: 前端不得为 UI 效果伪造消息时序

**消息类型**（前端需能处理）：

| 类型 | 方向 | 用途 |
|---|---|---|
| `user.message` | 用户 → 服务端 | 用户发消息 |
| `user.handoff` | 用户 → 服务端 | 快捷转人工，不经意图识别，不消耗 LLM |
| `assistant.delta` | 服务端 → 用户 | AI 流式片段 |
| `assistant.done` | 服务端 → 用户 | AI 输出结束 |
| `human.message` | 双向 | 人工发消息 / 用户收到 |
| `session.state` | 服务端 → 双方 | 状态变更（排队/接入/结束） |
| `queue.update` | 服务端 → 人工端 | 队列变化 |
| `agent.message` | 人工 → 服务端 | 人工发消息 |

**流程消息**（由 FR-023~028 派生，plan 细化）：`hello` / `ping` / `pong` / `error` / `user.message.ack`。

**查询接口**（由 FR-029~030 派生）：会话状态与历史、人工已接入会话列表。具体路径与结构见 `contracts/rest.md`。
