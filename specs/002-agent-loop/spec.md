# Feature Specification: Agent 主循环与状态机

**Feature Branch**: `002-agent-loop`

**Created**: 2026-11-09

**Status**: Draft — 待负责人审核

**Input**: 意图识别、工具调用编排、写操作确认

## 背景与目标

Feature 001 提供了四个业务能力（查订单、查物流、改地址、退款），但它们只是**被动的接口**：给什么参数查什么，不做判断。

本 feature 是第一个真正的消费方——用户用自然语言说一句话，系统判断他想干什么、需要哪些信息、该调哪个接口、拿到结果后怎么回复。

### 入口决定了大部分问题不用问

用户在**订单详情页**点击"联系客服"进入会话。这一刻前端已经知道是哪笔订单，并随会话建立一起传给 Agent：

```
前端传入：order_id + 商品快照（名称、金额、状态）
Agent 处理：以 order_id 查库为准，快照仅用于快速展示
```

**"请问是哪一笔订单"这个问题在正常路径上不需要问。** 用户说"我要退款"，Agent 直接拿会话绑定的订单去校验。

多轮交互的价值因此收窄到三个真实场景：参数补全、订单切换、写操作确认。

## 核心设计约束：意图识别必须由 LLM 主导

### 为什么规则不能主导

关键词只能说明"提到了"，不能说明"想干什么"。同样的词在不同语境下含义完全相反：

| 用户说 | 含关键词 | 真实意图 | 规则判定 | 后果 |
|---|---|---|---|---|
| "我要退款" | 退款 | 发起退款 | 退款 ✓ | 正确 |
| "再不处理我就投诉你们不肯退款" | 退款 | 威胁、施压 | 退款 ✗ | **误发起退款** |
| "这个能退款吗" | 退款 | 咨询可行性 | 退款 ✗ | 误弹确认 |
| "上次退款拖了半个月" | 退款 | 陈述历史 | 退款 ✗ | 误弹确认 |
| "别再发退款短信了" | 退款 | 反向表达 | 退款 ✗ | 严重误判 |
| "钱什么时候能回来" | 无 | 想退款 | 兜底 ✗ | **漏判** |
| "这个不能用" | 无 | 想退款 | 兜底 ✗ | **漏判** |

**两种错都不可接受**：
- 误判 → 在错误时机动钱，或让用户觉得被套话
- 漏判 → 表达不标准的用户得不到帮助，而且**是静默漏掉，你不知道漏了谁**

**关键区别**：如果系统只是给工单排序（错了代价小），规则主导尚可接受。但本系统要做**发起退款**这类不可逆的资金操作，**必须 LLM 主导**。

### 关键词的正确用法：辅助信号，不是决策依据

关键词表**不作为意图判定的依据**，而是作为给 LLM 的辅助提示：

```
用户说："你们再不给我处理，我就去投诉说你们不肯退款"
辅助提示：文本中出现了这些词 —— 退款, 投诉
LLM 判断：真实意图是投诉施压，不是发起退款
```

这样既利用了规则的确定性，又不让规则取代判断。

**不做"关键词预判决定是否调 LLM"**：那等于用弱判断决定要不要用强判断，弱判断错了强判断根本没机会执行，且漏判是静默的。

## User Scenarios & Testing

### User Story 1 - 语义优先的意图识别 (Priority: P1)

LLM 判断用户真实诉求，能区分诉求与威胁、否定、咨询、历史陈述、转述。

**Why this priority**: 整个 Agent 的地基。判断错了，后面每一步都错。

**Independent Test**: 一批包含正反表达的样本（"我要退款" vs "我就投诉说你们不肯退款" vs "这个能退款吗"），系统都能给出正确判断。

**Acceptance Scenarios**:

1. **Given** 会话绑定订单 ORD1002，**When** 用户说"我要退款"，**Then** 识别为退款诉求
2. **Given** 同上，**When** 用户说"你们再不处理我就投诉说你们不肯退款"，**Then** 识别为投诉/施压，**不进入退款流程**
3. **Given** 同上，**When** 用户说"这个能退款吗"，**Then** 识别为咨询，回答可否，**不弹确认**
4. **Given** 同上，**When** 用户说"上次退款你们拖了半个月"，**Then** 识别为投诉历史问题，不进入退款流程
5. **Given** 同上，**When** 用户说"钱什么时候能回来"，**Then** 识别为退款相关诉求
6. **Given** 同上，**When** 用户说"这个不能用"，**Then** 识别为售后诉求
7. **Given** 用户说"今天天气不错"，**Then** 不调用工具，进入澄清而非转人工
8. **Given** 用户说"这个东西不好用"，**When** 处理，**Then** **先道歉**再询问具体情况，**不提及任何业务动作**
8a. **Given** 用户说"随便说点什么"（无情绪），**When** 处理，**Then** 询问具体情况，**不道歉**
9. **Given** 已澄清 2 轮仍无法确定诉求，**When** 第 3 轮，**Then** 转人工
10. **Given** 用户说"我要转人工"或情绪激烈，**When** 处理，**Then** **跳过澄清**直接转人工

---

### User Story 2 - LLM 不可用时的安全降级 (Priority: P1)

LLM 超时、报错、返回不合法时，系统仍能工作，但**只做保守的事**。

**Why this priority**: 判断能力不可用时，绝不能靠关键词猜着去动钱。宁可让用户等，也不能错。

**Independent Test**: 模拟 LLM 完全不可用，写操作一律被拒，只读操作可以放行。

**Acceptance Scenarios**:

1. **Given** LLM 返回超时，**When** 用户说"我要退款"，**Then** **不发起退款**，回复"暂时无法处理，请稍后重试或转人工"
2. **Given** LLM 返回不合法结构，**When** 处理，**Then** 同样走降级路径
3. **Given** LLM 不可用，**When** 用户说"查下 ORD1003 物流"，**Then** 放行只读查询并如实返回
4. **Given** LLM 不可用，**When** 用户说"这个能不能退"（不含写词但意图是退款），**Then** 因未命中写操作词表而被放行到只读路径——**这是可接受的降级代价**，因为最坏结果只是多查一次只读数据
5. **Given** 降级期进行了处理，**When** 查看调用记录，**Then** 能看出本次请求是在降级模式下处理的
6. **Given** 上一次请求 LLM 超时，**When** 用户再发一条消息，**Then** 仍然先调用 LLM，不因上次失败而跳过

---

### User Story 3 - 写操作前的确认 (Priority: P1)

退款、改地址执行前必须让用户明确确认。

**Why this priority**: 已确认方案 A。这是防止误操作的最后一道闸。

**Independent Test**: 用户表达退款诉求后，系统复述待执行内容并等待确认，不直接执行。

**Acceptance Scenarios**:

1. **Given** 用户说"我要退款"，**When** 处理，**Then** 复述"即将为订单 ORD1002（¥259.90）提交全额退款，确认吗？"，**不调用退款接口**
2. **Given** 已发出确认请求，**When** 用户回复"确认"，**Then** 重新校验订单状态后执行
3. **Given** 已发出确认请求，**When** 用户回复"算了"，**Then** 取消，不调用
4. **Given** 已发出确认请求，**When** 用户回复无关内容，**Then** 重新确认，不默认同意
5. **Given** 确认请求发出 5 分钟以上，**When** 用户才回复确认，**Then** 重新校验后执行
6. **Given** 确认通过但执行前订单状态已变，**When** 执行，**Then** 拒绝并说明原因

---

### User Story 4 - 订单切换 (Priority: P2)

用户主动提到另一个订单号时，切换会话上下文。

**Independent Test**: 会话绑定 ORD1002，用户说"ORD1008 那个呢"，上下文切到 ORD1008。

**Acceptance Scenarios**:

1. **Given** 会话绑定 ORD1002，**When** 用户说"ORD1008 到哪了"，**Then** 切换并查 ORD1008 物流
2. **Given** 已切到 ORD1008，**When** 用户说"那退了吧"，**Then** 对 ORD1008 操作，不回到 ORD1002
3. **Given** 用户提到的订单号不存在，**When** 处理，**Then** 明确告知，**保持**原上下文
4. **Given** 用户提到他人订单，**When** 处理，**Then** 拒绝，提示无权限

---

### User Story 5 - 结果呈现与错误处理 (Priority: P2)

把工具返回的结构化结果转成用户能看懂的话。

**Independent Test**: 对每种结果码，系统都给出对应的自然语言回复。

**Acceptance Scenarios**:

1. **Given** 退款成功，**When** 回复，**Then** 包含退款金额与预计到账时间
2. **Given** 订单状态不允许退款（3001），**When** 回复，**Then** 用自然语言说明原因
3. **Given** 订单不存在（2001），**When** 回复，**Then** 明确说没查到，不编造
4. **Given** 物流暂无信息（2002），**When** 回复，**Then** 说"还没发货，暂时没有物流信息"，不是"查询失败"
5. **Given** 系统异常（4xxx），**When** 回复，**Then** 致歉说明，不暴露技术细节

---

### Edge Cases

- 会话绑定的订单在此期间被其他渠道退款（状态已变）
- 用户连续重复发送同一条消息（网络重试）
- 用户给出格式非法的订单号
- 用户先说要退款，确认环节又说"算了改地址吧"
- 单轮输入同时命中多个意图（"我要退款然后查物流"）
- LLM 返回超时或不可用
- 用户粘了一大段文本（超长输入）
- 用户使用的语言/方言模型理解不了

## Requirements

### Functional Requirements

**会话与入口**

- **FR-001**: 会话建立时必须绑定订单：`order_id` 由前端传入并作为锚点
- **FR-002**: 前端可同时传入商品快照，但**业务判断一律以查库结果为准**
- **FR-003**: 快照与库不一致时必须在调用记录中留痕，不得静默忽略
- **FR-004**: 会话绑定订单缺失时，必须追问订单号

**意图识别**

- **FR-005**: 意图识别**必须由 LLM 主导**，不得以关键词匹配结果作为判定依据
- **FR-006**: 系统必须能区分"诉求"与"威胁、否定、咨询、历史陈述、转述"，后者不得触发对应操作
- **FR-007**: 关键词表可作为**辅助提示**随用户输入一起提供给 LLM，但不得单独决定意图
- **FR-008**: 不得用关键词预判来决定是否调用 LLM
- **FR-009**: 识别结果必须包含意图、置信度、以及所用依据的可追溯信息
- **FR-010**: 单轮输入包含多个诉求时，必须明确只处理一个并告知用户，不得静默丢弃
- **FR-011**: 低置信度的写操作意图不得直接进入确认环节，应先澄清
- **FR-012**: 系统必须能从用户输入中提取订单号、金额等结构化参数

**无法识别时的处理：澄清优先，转人工是最后手段**

- **FR-016c**: "识别不到可调用的工具"**不等于**需要转人工，必须走澄清流程
- **FR-016d**: 澄清最多 2 轮；第 3 轮仍无法确定诉求时才转人工
- **FR-016e**: 澄清话术必须先确认方向（"您是想咨询订单问题，还是有其他需要帮忙的？"），再给有限选项（查订单 / 改地址 / 申请退款 / 其他）
- **FR-016f**: 以下情况**跳过澄清直接转人工**，它们对应 Feature 003 的触发源：
  - 用户明确要求人工
  - 情绪激烈（投诉、辱骂）
  - 工具连续失败
  - 涉及纠纷、监管投诉等超出能力边界的事项
- **FR-016g**: 澄清轮次计数必须记录在会话中，跨轮累计，不得每轮重置
- **FR-016h**: 澄清时**禁止主动提及任何业务动作**（退款、退货、退换、换货、改地址、补发、补偿、赔付），
  避免形成系统无权做出的承诺
- **FR-016i**: 用户表达负面情绪时，澄清必须先道歉再询问；情绪中性时不道歉
- **FR-016j**: 道歉措辞**统一一句**，不按情绪程度分级
- **FR-016k**: 第 2 轮澄清不再列业务选项，改为征求是否转人工
- **FR-016l**: 澄清时可以表达歉意、询问具体情况、说明会记录，但不得暗示处理结果

> 理由：转人工是有成本的资源。如果"AI 一时没理解"就转人工，
> 用户说一句"谢谢"也会被转接，人工成本会被无意义的转接吃掉。

**澄清话术的边界**

- **SC-009a**: 澄清话术中业务承诺词零出现（退款/退货/退换/换货/补发/补偿/赔付/帮您申请/保证）

> 理由：AI 说出的承诺与人工客服同等效力。一旦说"可以帮您申请退换"，
> 用户就会拿这句话要求退换，而本系统无权判断退换条件。

**操作安全分级**

- **FR-016h**: 操作风险分级不得按"操作类型"划分，必须按"**是否可逆 + 是否有前置条件**"划分
- **FR-016i**: 退款是"发起申请"，不是"执行退款"；资金何时真正变动不归本系统决定
- **FR-016j**: 改地址虽用户感知不敏感，但同样不可逆，必须：已发货时拒绝，未发货时允许，且**执行前必须确认**

**LLM 不可用时的降级**

- **FR-013**: LLM 不可用（超时、报错、返回不合法）时，**禁止执行任何写操作**
- **FR-014**: 降级时允许执行只读操作（查订单、查物流）。读写区分**只能基于关键词**，且必须遵守以下约束：
  - 命中写操作词表 → 一律拒绝，明确告知暂时无法处理
  - 未命中 → 允许走只读路径
  - **"未命中"不等于"确认是读操作"**，只是"没有理由认为是写操作"
  - 该降级判定必须记入调用记录，便于事后追溯哪些请求在降级期被处理
- **FR-014a**: 降级期使用的**写操作词表必须比正常路径的关键词表更宽**，宁可误拒只读请求，不可漏放写操作
- **FR-015**: 降级时必须明确告知用户当前无法处理写操作，并提供后续路径
- **FR-016**: 降级不得静默进行，用户必须能感知到系统当前的能力受限
- **FR-016a**: 降级期的关键词判定**不得用于任何写操作**，且其误判后果必须被限制为"多做一次只读查询"或"少做一次只读查询"，不得放大
- **FR-016b**: **每次输入都先调用 LLM，不做熔断跳过**。降级只在单次调用失败时触发：
  - LLM 调用超时、报错、返回不合法 → 本次请求走降级路径
  - **下一次请求仍然先尝试 LLM**，不因上次失败而跳过
  - 理由：意图判断的准确性优先于省调用。跳过 LLM 意味着用关键词替代判断，正是本 spec 要避免的
  - LLM 调用超时必须可配置，避免单次请求等待过久

**写操作确认**

- **FR-017**: 所有写操作（退款、改地址）执行前必须经过用户明确确认
- **FR-018**: 确认请求必须复述关键信息：订单号、金额、操作类型
- **FR-019**: 用户回复的非确认内容不得被当作同意
- **FR-020**: **执行前必须重新校验订单状态**，无论确认请求是否超时
- **FR-021**: 确认环节不得调用写接口

**订单切换与状态**

- **FR-022**: 用户提到另一个订单号时，上下文必须切换到该订单
- **FR-023**: 提到的订单不存在时保持原上下文不变
- **FR-024**: 不得允许跨用户操作订单
- **FR-025**: 会话状态必须存入 Redis，进程重启后可恢复
- **FR-026**: 会话状态必须包含：绑定订单、当前意图、待确认操作、轮次计数
- **FR-027**: 会话必须有 TTL，避免无限堆积

**结果呈现**

- **FR-028**: 每种业务结果码必须有对应的自然语言表达
- **FR-029**: 系统异常（4xxx）的回复不得暴露内部技术细节
- **FR-030**: 回复中不得出现未经工具确认的结论

**可观测**

- **FR-031**: 一次完整的用户输入必须产生一条贯穿 Agent 与 mock 服务的链路标识
- **FR-032**: 调用记录必须能看出意图识别方式（正常 / 降级）、工具调用次数、快照与库是否不一致

### Key Entities

- **会话**：会话 ID、用户 ID、绑定订单号、商品快照（仅展示用）、当前意图、待确认操作、轮次计数、降级标记、最后活跃时间
- **对话轮次**：所属会话、用户输入、识别结果（意图 + 置信度 + 依据）、抽取参数、工具调用、系统回复
- **待确认操作**：操作类型、目标订单、金额、发起时间、过期时间

## Success Criteria

### Measurable Outcomes

- **SC-001**: 从订单详情页进入的正常路径上，用户说"我要退款"后零追问直达确认环节
- **SC-002**: 一批包含威胁、否定、咨询、历史陈述、转述的样本，**零误判**（不得因关键词命中而触发操作）
- **SC-003**: 一批不含意图关键词但表达明确诉求的样本，**零漏判**
- **SC-004**: LLM 完全不可用时，**零写操作被执行**
- **SC-004a**: 上一次 LLM 失败不影响下一次请求尝试 LLM；连续失败后，下一次请求仍会先调用 LLM
- **SC-005**: 所有写操作 100% 经过确认环节且执行前重新校验
- **SC-006**: 每种结果码都有对应的自然语言回复，不暴露技术细节
- **SC-007**: 一次用户输入的完整链路可被单一链路标识检索到
- **SC-008**: 进程重启后会话可恢复

## Assumptions

- 意图识别需要可替换实现：生产用真实 LLM，测试用确定性桩（按输入返回预设结果，模拟各类判断）
- 测试不依赖真实 LLM 调用；真实 LLM 的准确率在评测集（Feature 007）衡量
- Redis 用于会话存储，单实例即可
- 只处理文本输入

## 范围外

- 转人工逻辑（Feature 003）
- SSE 流式输出（Feature 004）
- 前端界面（Feature 005）
- 评测集与自动回归（Feature 007）
- 多模型调度与成本优化（等评测有数据后再定）

## 已确认决策

| # | 问题 | 结论 |
|---|---|---|
| 1 | 前端传什么 | **order_id + 商品快照都传，业务判断以库为准** |
| 2 | 客服入口页面 | **订单详情页进入，会话默认绑定该订单** |
| 3 | 意图识别架构 | **LLM 主导，规则仅作辅助提示；LLM 不可用时降级且禁止写操作** |
| 4 | 会话状态 | **Redis** |
| 5 | 写操作确认 | **方案 A：用户须明确回复确认** |
| 6 | 执行前校验 | **始终重新校验订单状态** |
| 7 | 补全轮次上限 | **3 轮** |
| 8 | 降级期处理 | **方案 B：关键词区分读写，写操作一律拒绝，只读放行** |
| 9 | 降级词表 | **单独维护更宽的写操作词表，宁可误拒只读** |
| 10 | 降级触发方式 | **不做熔断。每次输入都先走 LLM，单次超时/失败才降级** |
