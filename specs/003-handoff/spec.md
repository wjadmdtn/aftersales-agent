# Feature Specification: 转人工链路

**Feature Branch**: `003-handoff`

**Created**: 2026-11-09

**Status**: Draft — 待负责人审核

**Input**: 四类触发源、上下文打包、优先级排队、人工接管

## 背景与目标

Feature 002 的 Agent 能处理标准诉求，但必然有处理不了的边界：查不到的东西、用户情绪激动、系统异常、用户明确要求人工。

**转人工不是兜底，是产品能力。** 做得差的转人工是 AI 说"正在为您转接人工"，然后用户等十分钟，人工接起来问"您好请问什么问题"，用户从头发一遍。

做得好的转人工：用户很快被接入合适的队列，人工客服屏幕上直接显示"退款问题，已查过订单 ORD1002（¥259.90，已发货），用户已确认要全额退款，情绪激动，建议直接退款并致歉"。

**这个 feature 的价值全在"转过去之后"**——上下文打包做得好，人工效率翻倍；做得差，等于把问题从头再来一遍。

## User Scenarios & Testing

### User Story 1 - 四类触发源 (Priority: P1)

系统在四种情况下发起转人工，每种的处理策略不同。

**Why this priority**: 单一"AI 答不上来就转"是玩具级做法。真实场景里，风险触发必须立刻转、用户主动要求必须不挽留、系统异常要先道歉再转。

**Independent Test**: 对每类触发条件构造输入，都能正确触发，且处理策略符合该类定义。

**Acceptance Scenarios**:

1. **Given** 用户说"转人工"，**When** 处理，**Then** 立即转接，不出现任何挽留话术
2. **Given** 用户说"我要投诉"，**When** 处理，**Then** 按风险触发转接，跳过后自助建议环节
3. **Given** 退款金额达阈值且命中投诉词，**When** 处理，**Then** 按风险触发，优先级为高
4. **Given** 工具连续失败达到阈值，**When** 处理，**Then** 先致歉说明，再转接
5. **Given** 工具返回"订单不存在"，**When** 处理，**Then** 先给出可能的自助方向，再转接
6. **Given** 用户说"转人工"但工具仍在执行，**When** 处理，**Then** 等待工具返回后终止，不硬切

---

### User Story 2 - 上下文打包 (Priority: P1)

转接时把人工作判断所需的信息结构化打包给人工客服。

**Why this priority**: 人工一次接待多个会话，不读摘要就要从头翻聊天记录。这是转人工体验的分水岭。

**Independent Test**: 转接后，人工端能拿到一份包含摘要、已尝试动作、优先级、触发原因的完整上下文。

**Acceptance Scenarios**:

1. **Given** 用户因退款问题转人工，**When** 转接，**Then** Context Pack 包含：摘要、已尝试的工具调用及结果、订单号、用户情绪、优先级、触发类型、AI 建议
2. **Given** 会话很长，**When** 生成摘要，**Then** 摘要不超过 120 字，且包含核心诉求与已尝试的处置
3. **Given** 是风险触发，**When** 打包，**Then** 不包含"AI 建议的下一步"
4. **Given** 订单已绑定，**When** 打包，**Then** 必须包含订单号
5. **Given** 未调用过任何工具，**When** 打包，**Then** 已尝试动作为空列表，不是缺字段

---

### User Story 3 - 优先级排队 (Priority: P1)

不同紧急程度的会话按优先级排队。

**Why this priority**: 投诉的用户和查订单的用户同时等待，先接查订单的是错的。

**Independent Test**: 多个会话同时排队，高优先级的先被接入。

**Acceptance Scenarios**:

1. **Given** 风险触发与用户主动要求同时排队，**When** 人工接入，**Then** 风险触发的先被接入
2. **Given** 同为高优先级，**When** 排队，**Then** 先进入队列的先接入
3. **Given** 用户情绪判定为激烈，**When** 计算优先级，**Then** 优先级为高，即使金额很小
4. **Given** 优先级计算，**When** 输出，**Then** 必须同时给出判定依据
5. **Given** 同一会话重复触发转人工，**When** 处理，**Then** 只占一个队列位

---

### User Story 4 - 人工接管与 AI 静默 (Priority: P1)

人工接入后，AI 完全退出，不得再发任何消息。

**Why this priority**: AI 在人工接待期间插话是严重事故——用户会看到两个"客服"同时说话。

**Independent Test**: 人工接入后，即使 AI 收到输入也不产生任何输出。

**Acceptance Scenarios**:

1. **Given** 会话在排队中，**When** 人工接入，**Then** 状态变为人工服务中
2. **Given** 已由人工接管，**When** 用户继续发消息，**Then** AI 不产生任何回复
3. **Given** 已由人工接管，**When** 系统尝试生成回复，**Then** 必须被拦截并记录为事故
4. **Given** 人工解决，**When** 会话结束，**Then** 状态变为已解决

---

### User Story 5 - 排队等待提示 (Priority: P2)

用户在排队时看到明确的当前状态，而不是无反馈的等待。

**Independent Test**: 用户转人工后，立即收到告知当前状态的提示，且后续重复询问时仍能得知状态。

**Acceptance Scenarios**:

1. **Given** 用户触发转人工，**When** 处理，**Then** 回复中明确告知"正在为您接入人工客服"
2. **Given** 用户已在排队中，**When** 再次发消息，**Then** 继续告知"正在为您接入，请稍候"
3. **Given** 人工已接入，**When** 用户发消息，**Then** AI 静默，由人工回复
4. **Given** 排队中，**When** 用户询问还要多久，**Then** 不承诺具体时间，只说明当前状态

> **已确认决策**：不提示预计等待时长。只告知"人工接入中"这一状态。

---

### Edge Cases

- 转接过程中用户撤回（"算了不用转"）
- 同一用户开多个会话同时转人工
- 人工接入瞬间用户又发了一条消息
- Context Pack 生成失败（摘要服务不可用）
- 队列为空时人工接入请求
- 用户 ID 缺失
- 会话在排队期间被人工从另一入口接入
- 用户连续多次说"转人工"

## Requirements

### Functional Requirements

**触发源**

- **FR-001**: 系统必须支持四类触发源：能力边界外、风险触发、用户主动要求、系统异常
- **FR-002**: 四类必须有互斥的判定顺序，同一输入命中多个时按固定优先级处理
- **FR-003**: 用户主动要求转人工时，**禁止出现挽留话术**
- **FR-004**: 风险触发时，**跳过自助建议环节**，直接进入排队
- **FR-005**: 系统异常触发时，必须先致歉说明再转接
- **FR-006**: 能力边界外触发时，先给出可能的自助方向再转接
- **FR-007**: 触发判定必须可配置（阈值、关键词、失败次数）

**情绪判定**

- **FR-007a**: 情绪判定**必须使用确定性规则**，不得调用 LLM
- **FR-007b**: 情绪判定规则至少包含：强烈负面词表、重复感叹号、连续大写/辱骂表达
- **FR-007c**: 情绪词表必须可配置
- **FR-007d**: 情绪判定失败或无法判定时默认为中性，不阻断转接流程

> 与 Feature 002 的意图识别采用不同策略：意图判错会动错钱，必须 LLM 主导；情绪判错只是优先级排序偏移，规则足够且确定。

**上下文打包**

- **FR-008**: 转接必须生成 Context Pack，包含：摘要、已尝试动作、订单号、意图、情绪、优先级、触发类型
- **FR-009**: 摘要不得超过 120 字，且必须包含核心诉求与已尝试处置
- **FR-010**: 摘要生成必须有**不依赖外部服务**的实现，确保打包永不失败
- **FR-011**: 风险触发时不得包含 AI 建议的下一步
- **FR-012**: 已尝试动作的结构必须包含：工具名、结果状态、时间
- **FR-013**: Context Pack 生成后只可追加，不可修改 AI 的原始判断

**优先级**

- **FR-014**: 优先级必须是**确定性规则计算**，不得由模型判断
- **FR-015**: 优先级输出必须同时给出判定依据
- **FR-016**: 判定顺序：风险触发 > 情绪激烈 > 金额超阈值 > 用户主动要求 > 其他
- **FR-017**: 同优先级必须按进入队列顺序排列
- **FR-018**: 同一会话重复触发只占一个队列位

**人工接管**

- **FR-019**: 人工接入只能由人工侧动作驱动，AI 不得自行推进
- **FR-020**: 人工接管后 AI **必须完全静默**，任何 AI 输出都视为事故
- **FR-021**: 静默约束必须有代码级拦截，不能只靠约定
- **FR-022**: 人工拒绝受理时，会话**不得回流给 AI**
- **FR-023**: 会话结束时状态必须变为已解决

**排队提示**

- **FR-024**: 用户触发转人工时，必须立即告知当前状态（人工接入中）
- **FR-025**: 排队期间用户再次发消息，必须继续告知当前状态
- **FR-026**: **不得承诺预计等待时长**
- **FR-027**: 用户询问还要多久时，只说明状态，不给时间承诺
- **FR-028**: 队列必须可查询深度与优先级分布

**可观测**

- **FR-029**: 转接全过程必须可通过链路标识检索
- **FR-030**: 转接事件（触发、排队、接入、拒绝、解决）必须全部留痕

### Key Entities

- **转接请求**：会话 ID、触发类型、触发详情、生成时间
- **上下文包**：摘要、已尝试动作、订单信息、意图与情绪、优先级与依据、触发信息、AI 建议
- **队列项**：会话 ID、优先级、进入时间
- **会话状态**：正常对话 / 排队中 / 人工服务中 / 已解决

## Success Criteria

### Measurable Outcomes

- **SC-001**: 四类触发源各自可独立验证，互不干扰
- **SC-002**: 用户主动要求转人工的场景下，挽留话术出现次数为 **0**
- **SC-003**: 人工接管后 AI 输出次数为 **0**
- **SC-004**: 同一会话重复触发转人工，队列中始终只有 1 条
- **SC-005**: 高优先级会话先于低优先级被接入
- **SC-006**: Context Pack 必填字段完整率 100%，摘要从不超长
- **SC-007**: 情绪判定全程零 LLM 调用
- **SC-008**: 转接全过程可用单一链路标识检出
- **SC-009**: 任何回复中不出现预计等待时长

## Assumptions

- 人工侧通过接口模拟（真实客服工作台是 Feature 005）
- 队列存 Redis，与会话存储共用
- 不做客服排班、技能路由、工作量均衡

## 范围外

- 客服工作台界面（Feature 005）
- SSE 流式输出（Feature 004）
- 真实人工坐席系统对接
- 转人工后的会话质检
- 预计等待时长估算

## 转接话术

| 场景 | 文案 |
|---|---|
| 用户主动要求 | 「好的，正在为您接入人工客服，请稍候。」 |
| 风险触发（投诉/情绪激烈） | 「非常抱歉给您带来了不好的体验，已为您优先接入人工客服，请稍候。」 |
| 系统异常 | 「抱歉，系统这边出了点状况，已为您接入人工客服协助处理，请稍候。」 |
| 能力边界外 | 「这个问题我这边没能处理，已为您接入人工客服，请稍候。」 |
| 排队中用户再发言 | 「正在为您接入人工客服，请稍候～」 |
| 排队中用户问要多久 | 「正在为您排队接入人工客服，接通的瞬间会自动通知您～」 |
| 人工拒绝/无法受理 | 「非常抱歉，这个问题需要升级到专员为您跟进，稍后会有同事联系您。」 |
