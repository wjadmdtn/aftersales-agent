# Feature Specification: 评测集与自动回归

**Feature Branch**: `004-evaluation`

**Created**: 2026-11-09

**Status**: Draft — 待负责人审核

**Input**: 标注集、指标定义、回归脚本、基线对比

## 背景与目标

前三个 feature 有 222 个测试，但它们验证的是"**代码按预期工作**"，不是"**系统效果好不好**"。

区别在这：

| 测试 | 评测 |
|---|---|
| Stub 返回退款 → 系统走退款流程 | 100 条真实用户表述里，有多少条被正确识别为退款 |
| 转人工后 AI 静默 | 100 条投诉样本里，有多少条被正确触发转人工 |
| 幂等只生效一次 | 并发 50 次时实际产生了几笔退款 |

**测试保证了正确性，评测回答了"多好"。** 简历需要的是后者——"意图识别准确率 87%"比"222 个测试通过"有说服力得多。

并且评测集是**回归的基准**：改了 prompt、换了模型、调了阈值，跑一遍就知道是变好了还是变坏了。

## User Scenarios & Testing

### User Story 0 - 意图分类的评测口径 (Priority: P1)

意图识别不能只分"对/错"，必须按**处理路径**分类。同一句"这个东西不好用"，
按不同口径评测会得到完全不同的结论。

**Why this priority**: 口径错了，220 条用例跑出来的数字没有意义。

**Independent Test**: 每条用例的预期结果都落在明确的一类里，且该类有对应的判分方式。

**Acceptance Scenarios**:

1. **Given** 用例预期为某个业务动作（查订单、查物流、改地址、退款），**When** 判分，**Then** 比对识别出的意图
2. **Given** 用例预期为"澄清"（识别不到工具但有明确信号），**When** 判分，**Then** 比对状态是否为澄清
3. **Given** 用例预期为"直接转人工"，**When** 判分，**Then** 比对是否入队而非澄清
4. **Given** 一条用例被误判成"转人工"而预期是"澄清"，**When** 判分，**Then** 单独标记为**过度转接**，与普通识别错误分列
5. **Given** 一条用例预期"澄清"而实际"转人工"，**When** 统计，**Then** 计入**人工成本损耗**指标

---

### User Story 1 - 评测用例格式 (Priority: P1)

定义每条评测用例的结构，使判分可以自动完成。

**Why this priority**: 格式定错了后面全要返工。这是整个 feature 的地基。

**Independent Test**: 每条用例都能被自动判分，不需要人工介入。

**Acceptance Scenarios**:

1. **Given** 一条意图识别用例，**When** 运行，**Then** 自动比对识别结果与预期，给出通过/失败
2. **Given** 一条转人工用例，**When** 运行，**Then** 自动比对是否触发、触发类型、优先级
3. **Given** 一条退款用例，**When** 运行，**Then** 自动比对最终订单状态与预期
4. **Given** 用例格式非法，**When** 加载，**Then** 启动即失败并指出哪一条有问题

---

### User Story 2 - 意图识别评测集 (Priority: P1)

覆盖"容易判错"的表达，而不只是标准说法。

**Why this priority**: 只测"我要退款"这种标准表达，准确率会虚高到 99%，毫无意义。

**Independent Test**: 能跑出意图识别的分类准确率，并列出判错的样本。

**Acceptance Scenarios**:

1. **Given** 标准表述（"我要退款""查下物流"），**When** 评测，**Then** 计入正常样本
2. **Given** 对抗表述（"再不处理我就投诉你们不肯退款"），**When** 评测，**Then** 计入对抗样本，且预期意图是投诉而非退款
3. **Given** 无关键词但诉求明确（"钱什么时候能回来"），**When** 评测，**Then** 预期意图为退款
4. **Given** 评测完成，**When** 输出报告，**Then** 包含总体准确率与**分类型准确率**
5. **Given** 有判错样本，**When** 输出报告，**Then** 列出每条的输入、预期、实际

---

### User Story 3 - 转人工评测集 (Priority: P1)

覆盖四类触发源和各类边界。

**Independent Test**: 能跑出转接触发准确率、触发类型归因准确率。

**Acceptance Scenarios**:

1. **Given** 应转人工的样本，**When** 评测，**Then** 检查是否触发，输出漏转率
2. **Given** 不应转人工的样本，**When** 评测，**Then** 检查是否误转，输出误转率
3. **Given** 触发的样本，**When** 评测，**Then** 检查触发类型是否正确
4. **Given** 触发的样本，**When** 评测，**Then** 检查优先级是否符合预期
5. **Given** 评测完成，**When** 输出报告，**Then** 误转率与漏转率**分别列出**，不合并成一个数字

> 误转浪费人工成本，漏转伤害用户体验，两者的业务代价不同，必须分开看。

---

### User Story 4 - 端到端任务评测 (Priority: P1)

从一句用户输入到最终业务状态，测整条链路。

**Independent Test**: 退款类用例能自动判定最终订单状态是否正确。

**Acceptance Scenarios**:

1. **Given** 一条受影响多轮的用例（表达 → 确认 → 执行），**When** 评测，**Then** 自动走完全流程并检查最终状态
2. **Given** 用例预期被拒（如订单已退款），**When** 评测，**Then** 检查订单状态未变
3. **Given** 评测完成，**When** 输出报告，**Then** 包含端到端成功率

---

### User Story 5 - 回归与基线对比 (Priority: P1)

改动之后跑一遍，能看出是变好了还是变坏了。

**Why this priority**: 没有基线对比，评测就只是一次性报告，不能用于"改动是否安全"的判断。

**Independent Test**: 改动后重跑，输出与上一条基线的逐项差异。

**Acceptance Scenarios**:

1. **Given** 存在上一版基线，**When** 跑新版本，**Then** 输出每个指标的增减
2. **Given** 某指标下降超过阈值，**When** 回归，**Then** 以非零退出码结束，阻断合并
3. **Given** 首次运行，**When** 无基线存在，**Then** 生成基线并提示
4. **Given** 指标提升，**When** 回归，**Then** 明确标示提升项
5. **Given** 总体准确率只降 1 个百分点（噪声范围内），**When** 回归，**Then** 不阻断
6. **Given** 出现一次 AI 静默违规，**When** 回归，**Then** 即使总体指标全升也必须阻断

---

### Edge Cases

- 评测用例数与预期不符（漏加载、重复 id）
- 某类样本数量过少（如只有 2 条对抗样本，准确率没意义）
- LLM 不可用时跑评测
- 评测耗时过长
- 同一条用例多次运行结果不同（LLM 非确定性）
- 基线文件格式版本不兼容
- 评测失败但业务系统本身正常

## Requirements

### Functional Requirements

**用例格式**

- **FR-001**: 每条用例必须是可自动判分的结构，不得依赖人工主观打分
- **FR-002**: 用例必须包含：唯一 ID、类别、输入、预期结果、判分断言
- **FR-003**: 用例文件格式非法时必须在加载阶段失败，并指出具体条目
- **FR-004**: 用例 ID 必须唯一，重复即失败
- **FR-004a**: 每条用例必须声明**预期处理路径**：业务动作 / 澄清 / 转人工 / 无关
- **FR-005**: 断言必须二元化（是/否），不得使用打分制

**意图识别评测**

- **FR-006**: 评测集必须覆盖：标准表述、对抗表述、无关键词诉求、无关输入
- **FR-006a**: 必须覆盖**应澄清**的样本，分为两类：
  - 有负面情绪（"这个东西不好用"）→ 预期：先道歉再询问
  - 无情绪（"随便说说"）→ 预期：询问，不道歉
- **FR-006b**: 必须覆盖**应直接转人工**的样本（四类触发源），且与"应澄清"严格区分
- **FR-006c**: 必须单独统计**过度转接率**——预期澄清但实际转人工的比例
- **FR-006d**: 澄清类用例必须断言话术**不含业务承诺词**（退款/退换/补偿等）
- **FR-006e**: 澄清类用例必须断言道歉的出现与否符合情绪判定
- **FR-007**: 必须输出总体准确率与**分类型准确率**
- **FR-008**: 必须列出每条判错样本的输入、预期、实际

**转人工评测**

- **FR-009**: 必须覆盖四类触发源各自的正例
- **FR-010**: 必须包含不应触发的负例
- **FR-011**: 必须分别输出**误转率**与**漏转率**
- **FR-012**: 必须输出触发类型归因准确率
- **FR-013**: 必须校验优先级是否符合预期
- **FR-013a**: 必须校验**转接前是否应先澄清**——"AI 没听懂"不得直接转人工

**端到端评测**

- **FR-014**: 必须能从一句输入驱动完整链路（含多轮）
- **FR-015**: 必须校验最终业务状态，不能只看回复文本
- **FR-016**: 被拒绝的操作必须校验**业务数据未变化**

**回归**

- **FR-017**: 必须支持保存基线
- **FR-018**: 必须支持与基线对比并输出逐项差异
- **FR-019**: 指标下降超过阈值时，进程必须以非零码退出
- **FR-019a**: 阈值必须**分类配置**，而不是统一一个数：
  - 总体指标（意图总体准确率、端到端成功率）：下降 ≥ 3 个百分点阻断
  - 关键单项（对抗样本准确率、误转率、漏转率）：恶化 ≥ 5 个百分点阻断
  - **硬性项（AI 静默违规、降级期写操作）：阈值为 0，出现一次即阻断**
- **FR-019b**: 阈值必须可配置，不得写死在代码里
- **FR-019c**: 阻断时必须明确输出"哪个指标、从多少降到多少、阈值是多少"，不能只给一个失败码
- **FR-020**: 报告必须可读，同时提供机器可读格式

**可重复性**

- **FR-021**: 评测必须同时支持两种 LLM 后端：
  - **stub**：确定性桩，用于 CI 回归，保证同一版本重复运行结果一致
  - **real**：真实模型，用于产出效果数字
- **FR-021a**: 两种模式下**用例、判分逻辑、报告格式完全一致**，只有 LLM 后端不同
- **FR-021b**: 报告必须明确标注本次评测用的是哪种后端
- **FR-021c**: stub 模式下的准确率**不得作为效果指标对外引用**，报告需显式提示
- **FR-022**: 每条用例必须从干净的初始状态开始，用例间不得互相污染
- **FR-023**: 每个用例的样本数必须可统计，样本过少时给出警告
- **FR-024**: 真实 LLM 模式下，必须记录每次运行的耗时与调用成本，便于评估评测可重复执行的代价

### Key Entities

- **评测用例**：ID、类别、子类、输入、预期结果、断言列表
- **评测结果**：用例 ID、通过与否、失败项、实际输出
- **评测报告**：总体指标、分项指标、失败明细、耗时
- **基线**：版本标识、时间、各指标数值

## Success Criteria

### Measurable Outcomes

- **SC-001**: 全部用例可自动判分，零人工介入
- **SC-002**: 报告同时给出总体与分类型指标
- **SC-003**: 误转率与漏转率分列，不合并
- **SC-003a**: **过度转接率**单独成项——预期澄清却转了人工的比例
- **SC-003b**: 澄清类用例的业务承诺词出现次数为 **0**
- **SC-004**: 回归能识别指标下降并以非零码退出
- **SC-004a**: 1 个百分点的噪声级波动不触发阻断；硬性项出现一次即阻断
- **SC-004b**: 阻断时能明确指出指标名、基线值、当前值、阈值
- **SC-005**: 同一版本重复运行，结果完全一致（确定性）
- **SC-006**: 用例间无污染，任意顺序运行结果相同
- **SC-007**: 能产出可直接用于简历/README 的指标数字，且数字来源标注为真实模型
- **SC-008**: 同一版本用同一后端重复运行，结果一致程度可观测（stub 完全一致；real 记录波动范围）

## Assumptions

- 用例由人工编写，覆盖真实用户表达
- 意图识别评测使用确定性桩，真实 LLM 的准确率由同一套用例在真实环境下另行跑
- 评测脚本可在 CI 中运行

## 范围外

- 真实 LLM 的自动调参
- A/B 实验
- 线上流量回流
- 人工标注平台

## 待确认项

1. **用例规模**（✓ 已确认）：**220 条**，按处理路径分布：

   | 类别 | 条数 | 说明 |
   |---|---|---|
   | 业务动作-标准 | 40 | 我要退款 / 查物流 / 改地址 / 查订单 |
   | 业务动作-对抗 | 30 | 威胁、否定、咨询、历史陈述、反向表达、转述 |
   | 业务动作-无关键词 | 20 | 钱什么时候能回来 / 这个不能用 |
   | **应澄清-有情绪** | 25 | 这个东西不好用 / 你们太慢了（预期：道歉+询问） |
   | **应澄清-无情绪** | 15 | 随便说说 / 嗯（预期：询问，不道歉） |
   | **应直接转人工** | 30 | 四类触发源各自的明确样本 |
   | 无关 | 20 | 天气 / 闲聊（预期：澄清，但不道歉） |
   | 端到端 | 40 | 多轮确认流程 + 最终状态校验 |

   合计 220 条。**澄清类共 60 条**，与转人工类 30 条严格区分。

2. **LLM 后端**（✓ 已确认）：**以真实 LLM 为准，桩仅用于 CI**
   - `--llm=real`：产出效果数字，简历与 README 引用此结果
   - `--llm=stub`：CI 回归用，验证链路正确
   - stub 结果的准确率不得对外引用，报告需显式标注后端

3. **回归阈值**（✓ 已确认）：分类配置
   - 总体指标下降 ≥ 3 个百分点阻断——容忍 LLM 噪声（同版本重跑通常差 1-2 点）
   - 关键单项恶化 ≥ 5 个百分点阻断——单项样本少波动大，但退步更危险
   - **硬性项阈值为 0**——AI 静默违规、降级期写操作，出现一次即事故，不设容忍
