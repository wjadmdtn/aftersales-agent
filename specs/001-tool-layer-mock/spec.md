# Feature Specification: 工具层与 mock 业务服务

**Feature Branch**: `001-tool-layer-mock`

**Created**: 2026-11-09

**Status**: Draft — 待负责人审核

**Input**: 为售后 Agent 提供可注入故障的订单、物流、地址、退款业务能力

## 背景与目标

售后 Agent 要处理"查订单、查物流、改地址、发起退款"这些业务动作。真实电商与物流平台的接口不会开放给个人项目，也无法在测试中制造"接口超时""重复提交""返回脏数据"这类场景。

因此需要两层：

1. **业务能力层**：Agent 可以调用的四个业务动作，每个动作有明确的输入、输出与失败语义
2. **mock 服务**：独立运行的假业务服务，模拟真实系统的行为，包括**故意制造故障**

这层的价值不在于"能查到订单"，而在于**让上层能够被验证**：转人工的四类触发、退款的幂等、状态机的降级，全都依赖这里的故障注入能力。没有可控的故障，上面这些能力都无法证明。

## User Scenarios & Testing

### User Story 1 - 查询订单与物流 (Priority: P1)

用户在订单页联系客服，Agent 需要先确认订单存在、状态是什么、货到哪了，才能判断能做什么。

**Why this priority**: 这是一切售后动作的前提。订单查不到或状态不明，后续退款、改地址都不该继续。它也是"能力边界外触发转人工"的主要来源。

**Independent Test**: 给定一批不同状态的订单，Agent 依次查询，每次都能拿到该订单的真实状态；查询不存在的订单时得到明确的"查不到"，而不是空值或异常。

**Acceptance Scenarios**:

1. **Given** 存在订单 A 且状态为已发货，**When** 查询该订单，**Then** 返回该订单的状态与金额，且结果被标记为成功
2. **Given** 订单号不存在，**When** 查询，**Then** 返回明确的"未找到"结果，而非空对象或抛异常
3. **Given** 订单已发货，**When** 查询物流，**Then** 返回当前物流节点与预计送达时间
4. **Given** 订单尚未发货，**When** 查询物流，**Then** 返回明确的"暂无物流信息"，与"查询失败"区分开

---

### User Story 2 - 发起退款 (Priority: P1)

用户要求退款，Agent 需要校验订单是否允许退款，然后发起退款。

**Why this priority**: 这是整个系统里唯一直接动钱的不可逆操作。幂等、金额校验、状态前置校验都必须在这里做扎实，否则上层所有的风险分级都失去意义。

**Independent Test**: 对同一订单连续发起两次退款，只有一次真正生效；对不允许退款的订单发起退款，被明确拒绝且不产生任何资金变动。

**Acceptance Scenarios**:

1. **Given** 订单已支付且未退款，**When** 发起退款，**Then** 退款成功并返回退款单号
2. **Given** 订单已退款完成，**When** 再次发起退款，**Then** 明确拒绝，且不产生第二笔退款
3. **Given** 同一笔退款请求被重复提交两次（相同请求标识），**When** 服务收到第二次，**Then** 返回第一次的结果，不重复执行
4. **Given** 订单状态为"未支付"，**When** 发起退款，**Then** 明确拒绝并说明原因
5. **Given** 请求的退款金额大于订单金额，**When** 发起退款，**Then** 明确拒绝

---

### User Story 3 - 修改收货地址 (Priority: P2)

用户下单后发现地址填错，希望在发货前修改。

**Why this priority**: 同样是不可逆操作（地址一旦修改影响履约），但风险低于退款。它的价值在于验证"有前置条件约束的操作"这一类模式，可以复用到其他场景。

**Independent Test**: 对未发货订单改地址成功并可查询到新地址；对已发货订单改地址被拒绝且原地址不变。

**Acceptance Scenarios**:

1. **Given** 订单未发货，**When** 修改为合法地址，**Then** 修改成功，再次查询订单可看到新地址
2. **Given** 订单已发货，**When** 尝试修改地址，**Then** 明确拒绝并说明"已发货不可修改"
3. **Given** 地址信息不完整（缺少必要字段），**When** 提交修改，**Then** 明确拒绝并指出缺什么

---

### User Story 4 - 故障注入与容错验证 (Priority: P1)

开发者需要在测试中主动制造"接口超时""重复响应""返回脏数据"等异常，验证上层的降级与转人工逻辑是否按预期工作。

**Why this priority**: 没有这一条，其余三条只是"能跑通的假接口"，无法支撑任何关于容错的声明。这是本 feature 区别于"玩具 mock"的核心。

**Independent Test**: 不修改任何业务代码，仅通过配置即可让指定接口在指定次数内失败、变慢、返回异常数据，且这些行为对调用方是真实网络请求的结果。

**Acceptance Scenarios**:

1. **Given** 配置了退款接口下次调用超时，**When** Agent 调用退款，**Then** 调用方收到超时结果，且订单状态未改变
2. **Given** 配置了订单接口返回不存在的数据，**When** 查询订单，**Then** 调用方收到明确的失败结果，而非伪造的成功
3. **Given** 配置了接口响应延迟，**When** 调用该接口，**Then** 实际耗时符合配置，可被上层超时机制捕捉
4. **Given** 故障只配置了一次，**When** 再次调用同一接口，**Then** 恢复正常行为
5. **Given** 没有任何故障配置，**When** 调用任意接口，**Then** 行为完全正常，故障注入不产生任何副作用

---

### Edge Cases

- 订单号格式非法（空、超长、含特殊字符）时的行为
- 退款金额为 0 或负数
- 退款金额恰好等于订单金额、恰好等于订单金额 + 0.01
- 同一订单并发发起两次退款
- 物流接口返回了订单状态为"未支付"的订单（数据不一致）
- 故障注入配置了不存在的接口名或非法参数
- mock 服务重启后，已注入的故障配置与业务数据是否保留
- 地址修改为与原地址完全相同（是否视为成功）
- 服务不可达（连接失败）与接口返回失败的区别是否可被调用方区分

## Requirements

### Functional Requirements

**业务能力**

- **FR-001**: 系统必须提供查询订单的能力，返回订单状态、金额、收货地址
- **FR-002**: 系统必须提供查询物流的能力，返回物流节点与预计送达时间
- **FR-003**: 系统必须提供发起退款的能力，返回退款单号与处理状态
- **FR-004**: 系统必须提供修改收货地址的能力
- **FR-005**: 每个业务能力必须返回**可区分的结果状态**：成功、未找到、业务拒绝（带原因）、系统异常。调用方必须能仅凭返回值判断走哪条分支，不需要解析错误文本
- **FR-006**: 订单不存在时的结果必须与"接口失败"明确区分（前者是"没有这个订单"，后者是"没查到"）

**安全与一致性**

- **FR-007**: 退款必须幂等。同一笔退款请求重复提交，只能产生一笔实际退款，且后续提交返回首次的结果
- **FR-008**: 退款前必须校验订单状态允许退款，不允许的订单必须拒绝且不产生任何资金变动
- **FR-009**: 退款金额必须校验不超过订单金额，且必须为正数
- **FR-010**: 修改地址前必须校验订单状态允许修改
- **FR-011**: 所有业务能力必须以订单 ID 为准，不接受仅凭用户 ID 操作他人订单

**故障注入**

- **FR-012**: 系统必须支持按接口配置故障，至少包含：超时、返回错误、返回脏数据、延迟
- **FR-013**: 故障必须可配置触发次数（一次性 / 持续），触发完毕后自动恢复正常
- **FR-014**: 故障注入必须通过配置生效，**不得要求修改业务代码**
- **FR-015**: 故障注入不得改变业务数据的一致性（例如超时的退款请求不能留下"钱退了但状态没变"）

**可观测**

- **FR-016**: 每次业务调用必须产出可追溯的记录，包含：调用了哪个能力、入参、结果状态、耗时、是否被故障注入影响

### Key Entities

- **订单**：订单号、状态（待支付 / 已支付 / 已发货 / 已完成 / 已关闭 / 退款中 / 已退款）、金额、收货地址
- **物流信息**：关联订单、当前节点、预计送达时间、轨迹列表
- **退款单**：退款单号、关联订单、金额、状态、请求标识（用于幂等）、创建时间
- **地址**：收件人、联系电话、省市区、详细地址
- **故障配置**：目标能力、故障类型、触发条件、持续次数

## Success Criteria

### Measurable Outcomes

- **SC-001**: 覆盖全部四个业务能力的正常与异常分支，每条分支都有可自动验证的用例
- **SC-002**: 退款幂等在**并发场景**下依然成立（同一请求标识并发提交 N 次，只产生 1 笔退款）
- **SC-003**: 四类故障（超时 / 错误 / 脏数据 / 延迟）均可仅通过配置触发，无需改代码
- **SC-004**: 故障触发后自动恢复，连续调用 N 次中恰好只有配置的次数受影响
- **SC-005**: 业务拒绝与系统异常的返回结果在**结构上可区分**，调用方无需解析文本
- **SC-006**: 全部业务能力均有调用记录，且记录中能看出该次调用是否被故障注入影响

## Assumptions

- 业务数据以预置的固定数据集为主，不需要完整的增删改查后台；数据可通过配置或文件初始化
- mock 服务与 Agent 层通过真实网络请求交互（HTTP），不是进程内的函数调用——只有这样才能真实覆盖超时、序列化、连接失败等问题
- 不接入任何真实电商或物流平台
- 单用户单订单场景即可，不需要处理复杂的用户体系与权限模型
- 退款金额单位与精度沿用电商惯例（元，两位小数）

## 范围外

- 真实支付渠道对接
- 订单创建、取消等售前/下单流程
- 物流轨迹的实时推送
- 多租户与权限体系
- 售后工单的管理后台

## 待确认项

以下需要负责人决定，确认前不进入 plan 阶段：

1. **业务数据是否需要跨重启保留**（✓ 已确认：内存 + 种子文件，见下方结论）
   - 指"订单、退款单、地址"这些被 mock 服务管理的数据。两种做法：启动时从种子文件读进内存，运行中改的只在内存里，重启回到种子状态（每次评测都从干净状态开始）；或者落盘到数据库，重启后保留，能复现某个具体问题但需要手工清理。
   - **结论**：启动从种子文件加载，运行中只改内存，重启回到种子状态。
2. **并发退款的幂等策略**（✓ 已确认：请求标识）
   - **结论**：以调用方传入的请求标识去重。同一标识重复提交返回首次结果，不重复执行。
3. **地址修改为完全相同的内容**（✓ 已确认：视为成功且不写库）
   - **结论**：返回成功，不产生写操作。
4. **故障注入的作用域**（✓ 已确认：按请求维度）
   - 指"制造故障"这件事影响谁。全局生效：一旦开启，所有调用这个接口的人都受影响，适合手工演示"接口挂了会怎样"；按请求维度：只有带特定标记的那一次调用受影响，其他调用正常，适合评测里精确控制"只让这一个用例失败"。
   - **结论**：按请求维度。调用时携带故障标记，仅该次调用受影响。
