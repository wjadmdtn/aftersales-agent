# 售后客服 Agent Constitution

一个面向售中 / 售后的客服 Agent。它的价值不在"能聊天"，而在**不可逆操作可控**、**AI 处理不了时能平稳移交人工**、**每一项能力都有可自动判分的验证**。

## Core Principles

### I. 规范先行（NON-NEGOTIABLE）

任何功能都必须先有 spec，经确认后才能写测试，测试通过后才能写实现。

- spec 描述"做什么、为什么"，不写技术细节
- plan 描述"怎么做"，含技术选型、数据结构、约束
- tasks 拆成可独立实现、可独立验证的小块
- **不跳过任何阶段**。一次性交付多个模块等于没有流程
- 实现中发现 spec 有误，先改 spec 并重新确认，不接受"代码写完再补文档"

理由：本项目在引入流程前曾一次性写出 1139 行未经审核的代码（见 `_prototype/`），其中包含至少一处自相矛盾的测试断言。流程不是形式，是防止这类问题的唯一手段。

### II. 测试即验收标准（NON-NEGOTIABLE）

每条 spec 里的验收条件，必须在测试里有对应断言。没有对应测试的验收条件视为未实现。

- 测试先于实现（Red → Green → Refactor）
- 涉及资金、越权、状态机流转的路径必须标记为一票否决项
- 测试必须能独立运行，不依赖执行顺序或共享状态
- **禁止为凑绿而改断言**。断言与 spec 冲突时，先判定是 spec 有误还是实现有误：
  - spec 有误 → 修改 spec 的对应验收条件，**须经项目负责人确认**，再同步改断言，并在提交信息里写明原因
  - 实现有误 → 改实现，不动断言
  - 不允许只改断言不改 spec，也不允许两边都改却不说清楚为什么

### III. 规则可解释、可复现

凡是影响**真人**的决策（转人工优先级、工单分派、金额阈值判断），必须是确定性规则，不能交给模型判断。

- 判定逻辑写成纯函数，可单测、可追踪
- 每个判定结果必须携带"为什么"（如 `priority_reason`）
- 模型可以建议，但不能作为最终裁决

理由：优先级决定客服先接哪个用户，出错无法向主管解释，也无法复现。

### IV. 配置外置，代码不收硬编码

阈值、关键词、超时时间、队列参数一律通过配置注入，代码中不出现字面量。

- 默认值可以有，但必须可覆盖
- 配置项需要校验，非法配置在启动时失败而不是运行中静默出错
- 每个配置项都要有测试证明"改了就生效"

### V. 边界诚实

系统对外承诺的能力必须与实现一致。

- 做不到的功能不写进文档，也不留半成品接口
- 降级、兜底、失败必须有明确行为和提示，不静默
- 数据缺失时返回空，不拼凑语义不同的替代数据

理由：客服场景里"错误地回答"比"说不知道"伤害大得多。

## 技术约束

**后端技术栈**：Python 3.11+、FastAPI、Pydantic v2、Redis、pytest

**前端技术栈**：Vue 3 + TypeScript + Vite（与项目负责人既有技术栈一致）

**依赖管理**：
- 新增第三方依赖必须在对应 spec 或 plan 里说明用途与替代方案，不得凭习惯引入
- 能用标准库或已有依赖实现的不引入新依赖
- 依赖需锁定版本，提交 lock 文件

**结构约定**：
- 领域模型与业务逻辑分离，不把 HTTP 细节渗透进状态机
- 外部依赖（LLM、业务 API）必须定义接口，实现可替换
- mock 服务支持故障注入（超时、重复、脏数据、超限），用于验证容错路径

**禁止**：
- 真实接入第三方电商 / 物流平台 API
- 用户侧产品能力（注册登录、商品浏览、下单、支付）
- 在 spec 之外自行扩大范围

**客服对话页面（允许，是项目的一部分）**：
提供一个面向客服 / 用户两端的对话页面，按真实客服产品的交互来设计。

功能范围：
- 流式对话：用户发消息，AI 回复以 SSE 流式逐步输出
- 快捷转人工：对话内可一键转人工，不需要打字
- 五类状态可视化：AI 接手中、排队等待、人工接手中、已解决，用户在界面上能看清当前由谁在服务
- 人工端：能看到 Context Pack（摘要、已尝试动作、优先级、触发原因），并能接入 / 拒绝
- 内置观察视图：会话状态流转、转人工队列、trace 时间线

明确不做：注册登录、商品浏览、下单支付、多渠道接入、客服排班与绩效

工程约束：
- 页面调用的必须是真实业务接口与状态机，不得为页面单独开后门接口；页面上能走通的路径，就是系统真实支持的路径
- 独立前端工程，与后端解耦：可单独构建，产物打进后端镜像静态目录；后端不依赖前端构建即可启动与测试
- 前端工程纳入 CI：构建失败阻断合并
- 流式输出必须使用后端原有的 SSE 接口，不在前端伪造打字效果

**判断标准**：这个页面要能让评审者不读文档、直接操作就理解系统在做什么。做不到说明设计有问题，而不是页面做得不够花哨。

## 开发流程

1. `spec` → 负责人审核 → `plan` → 负责人审核 → `tasks` → 逐个实现
2. 每个 task 完成后跑定向测试，全部 task 完成后跑全量测试
3. 提交信息说明"为什么"，而非"改了什么"
4. 每个 feature 完成后更新 README 的进度与范围说明

**排期顺序（前端提前）**：
前端与后端并行推进，前端先于后端完成交互骨架，后端接口就绪后接入真实数据。

- 前端第一阶段：搭工程 + 交互骨架（流式对话、快捷转人工、状态可视化），用 mock 数据跑通
- 后端按 feature 逐步交付，接口可用后前端逐个替换 mock
- **替换 mock 时必须有对应的端到端验证**，确保页面走的是真实链路
- 前端工程从第一阶段起纳入 CI

## Governance

本宪法优先于任何临时做法。如需偏离，必须在 spec 中写明理由并**经项目负责人确认**。

**spec 变更规则**：
- spec 的任何修改（含验收条件的增删改）都必须先向项目负责人说明改什么、为什么改，**确认后才写入**
- 实现过程中发现 spec 有缺陷，先停下来说明问题，不得自行放宽或补充验收条件
- 修改宪法需同时更新版本号与日期，并检查已有实现是否仍然合规
